# 04: A deliberate violation, caught

A domain with an internal resource, and a sibling domain that reaches straight into it —
once by a plain function call, once by a genuine Ash relationship — with the compiler
catching both. This is sample project 4 of 4 from the AshBoundary project goal, and it is
the payoff: samples 1–3 built up the vocabulary (default enforcement, exported vs.
internal, the calculation-based decoupling pattern); this one is where the whole library
either earns its keep or doesn't.

Unlike samples 1–3, whose own point was something else and which only used a caught
violation as illustrative, README-only context, this example's entire reason to exist
*is* a caught violation. So it is not left as a scratch file the reader has to create by
hand to believe: `test/deliberate_violation/violation_test.exs` shells out to a real,
isolated `mix compile --warnings-as-errors` and asserts on the real exit code and real
output, every time `mix test` runs. See "How the violation is isolated and proven" below
for why, and how that compares to example 3's approach to the same problem.

## The domains

| Module | Exported? | Role |
| --- | --- | --- |
| `DeliberateViolation.Accounting` | yes (a boundary's root always is) | domain that owns ledger data |
| `DeliberateViolation.Accounting.LedgerEntry` | **no** | the real, ETS-backed resource. Has its own `code_interface` (`create`, `read`) for use inside the domain |
| `DeliberateViolation.Accounting.Summary` | yes | the domain's entire public API: two generic actions, `:record` and `:total` |
| `DeliberateViolation.Billing` | yes | domain that owns invoices, shipped clean. `boundary do deps [...Accounting] end` |
| `DeliberateViolation.Billing.Invoice` | yes | has `attribute :ledger_entry_id, :uuid` — no relationship — and a `:ledger_total` calculation that calls `Accounting`'s **exported** `Summary` facade |
| `DeliberateViolation.Violation.Billing` | yes | **not compiled by any normal build.** Same domain as `Billing`, same honest `deps` line, reaching past it anyway |
| `DeliberateViolation.Violation.Billing.Invoice` | yes | the alias-style violation: `belongs_to :ledger_entry, ...Accounting.LedgerEntry` |
| `DeliberateViolation.Violation.Billing.LedgerEntryCaller` | — | the call-style violation: `LedgerEntry.create!/1`, called directly |
| `DeliberateViolation` | — | the app's root boundary, plain `use Boundary`, mandatory in every example (see sample 1) |

This mirrors example 3's shape deliberately: `Accounting`/`LedgerEntry`/`Summary` here
play the exact role `Customers`/`Customer`/`Directory` play there, for the same reason —
a facade resource keeps the exported surface equal to the interface, so `LedgerEntry`
stays internal no matter what any other domain declares. See that example's "Design
note: why a facade resource rather than `define`s on `Customer`" for the full rationale.

## Two ways in, both caught

`DeliberateViolation.Billing` is shipped clean: it never mentions `LedgerEntry` anywhere.
`DeliberateViolation.Violation.Billing` is the same domain with two lines changed, one
per way of reaching into another boundary's internal module.

**The alias-style violation** — `violation/billing/invoice.ex`:

```elixir
relationships do
  belongs_to :ledger_entry, DeliberateViolation.Accounting.LedgerEntry do
    allow_nil? false
    attribute_writable? true
    public? true
  end
end
```

A relationship names a module and calls nothing on it — no `Module.function()` anywhere —
which is exactly the kind of reference `boundary` does not check by default
(`check: [aliases: false]` is its documented default, per example 3's "Alias checking is
on by default" section). **AshBoundary enables alias checking for every domain it
manages, with zero project-level `mix.exs` configuration**, which is the only reason this
`belongs_to` is caught at all. This example's `mix.exs` sets no
`boundary: [default: [check: ...]]` of any kind — that is deliberate, not an oversight:
the whole point is that this now works out of the box.

**The call-style violation** — `violation/billing/ledger_entry_caller.ex`:

```elixir
alias DeliberateViolation.Accounting.LedgerEntry

def run do
  LedgerEntry.create!(%{description: "Reached in directly", amount: 0})
end
```

`create!/1` is real. It is generated by `LedgerEntry`'s own `code_interface`, exactly as
in sample project 2, and it would return a real, valid record if this call were allowed
to run. `boundary` never asks what the function does or how it came to exist — only
whether `DeliberateViolation.Accounting.LedgerEntry`, the module, is exported by its
owner boundary. It isn't, so the call is forbidden regardless.

**Both are caught by one command**, run against the isolated `violation/` tree (see
below):

```
$ MIX_ENV=violation mix compile --warnings-as-errors
...
warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
  (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
  violation/billing/invoice.ex:36

warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
  (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
  violation/billing/ledger_entry_caller.ex:18
```

This exits `1`. `boundary` prints nothing further after the two warnings — there is no
trailing "Compilation failed due to warnings..." summary line for this kind of warning
(unlike some other warning types, which do log a separate summary). The exit code is `1`,
which is what `--warnings-as-errors` actually depends on to fail the build.

Without `--warnings-as-errors`, the same command reports the same two warnings verbatim
and exits `0`:

```
$ MIX_ENV=violation mix compile
...
warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
  (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
  violation/billing/invoice.ex:36

warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
  (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
  violation/billing/ledger_entry_caller.ex:18
```

`boundary` reports a cross-boundary violation as a **compiler warning**, not a hard
failure, by default — this is the single detail every example in this series has had to
account for, and this is the example where it matters most: without
`--warnings-as-errors`, "the compiler catches it" is true only in the sense that it *told
you*, not that it stopped anything. A CI pipeline (or any gate) that runs plain
`mix compile` and calls a clean exit code good news would let both of these violations
through. `--warnings-as-errors` is what turns the warning into something a build can
actually fail on — which is exactly why every example in this series, including this
one's own gate below, runs with that flag.

Everything above is real, captured output — see "How the violation is isolated and
proven" for exactly how it was captured, by the same subprocess this example's own test
suite runs.

## The contrast case: reaching into what IS exported

`DeliberateViolation.Billing.Invoice`'s `:ledger_total` calculation
(`lib/deliberate_violation/billing/calculations/ledger_total.ex`) is the same shape of
cross-domain call as the violation above — a module outside `Accounting` calling into
it — except it calls the *exported* `DeliberateViolation.Accounting.ledger_total!/0`:

```elixir
alias DeliberateViolation.Accounting

@impl Ash.Resource.Calculation
def calculate(invoices, _opts, _context) do
  total = Accounting.ledger_total!()
  {:ok, Enum.map(invoices, fn _invoice -> total end)}
end
```

`DeliberateViolation.Billing` declares `boundary do deps [DeliberateViolation.Accounting]
end`, same as `DeliberateViolation.Violation.Billing` does — the `deps` line is identical
between the clean domain and the violating one. The only thing that differs is which
module on the other side of the line gets referenced: `Accounting` (exported) versus
`Accounting.LedgerEntry` (not). `mix compile --warnings-as-errors` against the shipped
`lib/` tree exits `0`, with no warnings, and `mix test` (below) proves the calculation
genuinely returns a value computed from the other domain's ETS-backed data — not a stub.

This is the other half of "the compiler doing its job": it stays out of the way,
silently, for every reference that respects the boundary, and only speaks up for the two
that don't.

## Running it

```
mix deps.get
mix format --check-formatted
mix compile --warnings-as-errors
mix test
```

`mix deps.get` must run before `mix format --check-formatted`: `.formatter.exs`'s
`import_deps` needs the deps actually present on disk to resolve, and fails with
`Unknown dependency :ash given to :import_deps` on a clean checkout otherwise. All four
succeed — this is what "the example's own build stays green" means here: nothing in
`lib/` or in this default `mix test` run is expected to fail. `mix test` runs four tests,
in two files:

- `DeliberateViolation.BillingTest` proves the clean, shipped state works end to end:
  a ledger entry is recorded through `Accounting`'s exported `Summary` facade, an
  invoice is issued through `Billing`'s exported interface, and loading
  `:ledger_total` returns a real value computed from the other domain's ETS table.
- `DeliberateViolation.ViolationTest` is the automated proof described above — it is
  also part of this same, green `mix test` run, because what it proves ("the isolated
  `MIX_ENV=violation` build fails in exactly the documented way") is itself a passing
  assertion, not a failing build. See the next section.

## How the violation is isolated and proven

`violation/` holds the deliberately-coupled `DeliberateViolation.Violation.Billing`
domain — real, complete code, not a fragment. `mix.exs` keeps it out of every normal
build the same way example 3 keeps `antipattern/` out of its own:

```elixir
defp elixirc_paths(:violation), do: ["lib", "violation"]
defp elixirc_paths(_env), do: ["lib"]
```

So far this is identical to example 3's approach, and for the same reason: `boundary`
reports violations as warnings, and this project's own `mix compile`/`mix test` gate has
to stay green the same as every other example's, so code that is *expected* not to
compile under `--warnings-as-errors` cannot live in the paths those commands touch.

**Where this example departs from example 3 is what proves the isolated build actually
fails.** Example 3's `antipattern/` is verified by a documented, reproducible README
walkthrough — a human (or a reviewer) runs `MIX_ENV=antipattern mix compile
--warnings-as-errors` themselves and reads the output. That is the right amount of
ceremony there, because example 3's whole point is the decoupling pattern; the
antipattern build failing is supporting evidence for that point, not the point itself.

Here, the point of the *entire example* is that a violation gets caught. Leaving that to
a manual reproduction step would mean the one thing this sample project exists to
demonstrate is the one thing nothing automatically checks — exactly the gap
`examples/01_basic_boundary`'s README flags when it says sample project 4 "is expected to
need its own approach to make that automated." So `test/deliberate_violation/violation_test.exs`
shells out to the isolated build itself, as a subprocess, from inside an ordinary
`ExUnit` test that `mix test` runs every time:

```elixir
{output, exit_code} =
  System.cmd("mix", ["compile", "--warnings-as-errors"],
    cd: File.cwd!(),
    env: [{"MIX_ENV", "violation"}],
    stderr_to_stdout: true
  )

assert exit_code == 1
assert output =~ """
       warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
         (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
         violation/billing/invoice.ex:36\
       """
assert output =~ """
       warning: forbidden reference to DeliberateViolation.Accounting.LedgerEntry
         (module DeliberateViolation.Accounting.LedgerEntry is not exported by its owner boundary DeliberateViolation.Accounting)
         violation/billing/ledger_entry_caller.ex:18\
       """
```

A second test in the same file makes the same call without `--warnings-as-errors` and
asserts the inverse: exit `0`, same warnings present. Together the two tests are the
`exit 0` vs. `exit 1` distinction explained above, as executable assertions rather than
README prose.

**Why a subprocess**, rather than something in-process like `Code.compile_file/1` on the
violating modules directly: `boundary`'s forbidden-reference check is wired in as a Mix
*compiler* (`compilers: [:boundary] ++ Mix.compilers()`), which runs as a distinct step
in a `mix compile` invocation — not as a check inside the modules being compiled, and not
something `Code.compile_file/1` triggers on its own. A real, separate `mix compile` run
is the only thing that genuinely exercises it, so that is what the test runs, against a
genuinely separate `MIX_ENV` and `_build/violation/` so it cannot disturb this example's
own shipped build artifacts.

One practical consequence: the first time `mix test` runs against a fresh checkout, that
subprocess has to compile this project's dependencies for the `:violation` env from
scratch (mirroring example 3's note about its own `antipattern` env), which can take
roughly a minute. Every run after that reuses `_build/violation/` and is fast. The test
carries a five-minute timeout to accommodate the cold-start case.

## Gate

Same as every example in this series, run from within this directory:

```
mix deps.get && mix format --check-formatted && mix compile --warnings-as-errors && mix test
```

**What "green" means for an example whose whole point is a violation:** this gate itself
must be green, unconditionally — `mix compile --warnings-as-errors` here compiles only
`lib/` (via `elixirc_paths`) and must exit `0` with no warnings, and `mix test` must pass,
including `DeliberateViolation.ViolationTest`. That test passing *is* the demonstration:
it means the separate, isolated `MIX_ENV=violation mix compile --warnings-as-errors`
genuinely exited `1` with the two expected warnings when it was invoked. A green result
on *that* isolated, `violation`-env build — the one thing this gate never runs directly
— would mean the violation was not caught, which is the failure mode this whole example
exists to prevent. `violation/` is format-checked (it is listed in `.formatter.exs`
inputs) but, like `antipattern/` in example 3, is never compiled by the default `:dev`
or `:test` env, which is the whole reason the violation can ship as real, complete code
rather than a prose description of one.

See `examples/01_basic_boundary/README.md`'s "Conventions for other examples" section for
the full set of structural conventions this example follows (standalone Mix project,
committed `mix.lock`, mandatory root `use Boundary` module, and so on) — they apply here
without modification.
